Git Commit Summary
Our team, Oreo Mcflurry, made 33 commits on GitHub from May 15 to August 7. We worked on the project in three main stages: planning, backend, and features.
Stage 1 — Planning
At the beginning, we worked on planning the project instead of jumping straight into code. This is normal for most software projects, since it's easier to fix problems on paper than after something is already built. We created a Survey document to look at similar apps and ideas before we started. After that we made the Actor & Feature List, which listed out who would use the app (like guests and users) and what features they would need, such as searching restaurants and saving favorites. We also uploaded a CS225 document and later added the SRS (Software Requirements Specification), which explained the requirements for the whole system in more detail so everyone knew what "done" looked like for each feature.
Alongside these documents, we kept updating the README multiple times. Early on this was just to set up the project description, but later we used it to divide the work between team members and list each person's assigned module, like Search, Favorites, and Sorting. This stage didn't add a lot of lines of code, but it mattered a lot because it gave the team a shared plan so we weren't building things that didn't match up with each other later.
Stage 2 — Backend
The backend stage started with one big commit from Edrien that set up Express, Prisma, and PostgreSQL, plus the starting React app made with Vite. This was the single biggest commit in the whole project, adding about 2,900 lines in one go, since it included the server files, the database schema, the folder structure for the client app, and basic styling. This commit was important because almost every other feature in the app depended on it — without a working backend and database connection, nobody could actually connect their frontend pages to real data.
After the backend was in place, we added API routes for restaurants and favorites, which are the endpoints the frontend uses to fetch and save data. We also added a seed file, which fills the database with sample restaurant data so we had something real to test with instead of empty pages. We renamed a few files during this stage too, just to keep our documents organized and easy to find in the repo.
Stage 3 — Features
This was the busiest stage of the project, where most of the actual app features got built. Edrien fixed CORS errors that were blocking the frontend from reaching the backend, and added React Router so users could move between pages properly.
Rajvir built the Search page from scratch, both the layout (CSS) and the logic (JSX). She also fixed some smaller issues afterward, like making the search show all restaurants when the search box is empty, and changing the "no results" message so it tells users to try a broader search instead of just saying nothing was found.
Gursharn worked on the sort and display feature, so users could sort search results (for example, by rating or newest). Later, Gursharn also cleaned up the code by moving the restaurant list into its own reusable component, so the same list layout could be used in more than one place without repeating code.
My assigned part was Favorites & Share, which covered things like the bookmark control, checking that a user is logged in before they can favorite something, making sure favorites actually stay saved, showing a saved state visually, and letting users access their favorites list from other pages. This came together as a Favorites page with a card layout and a loading spinner, a heart-shaped bookmark button added to the search results so users could save a restaurant right from search, and a link back to the Favorites page so it was easy to find saved restaurants again. I worked through these requirements with the team and helped shape how the Favorites page ended up working. Vitumbiko also helped keep the README and project documentation accurate during this stage, fixing team member IDs and formatting. We also added supporting documents like the Discovery Design Document and the Database Test Report to keep track of decisions and testing.
