## 1. Contribution to Team Discussions

As part of Team XOR I took part in the team meetings in May where we decided how the moderation system should be split across the group and set up the shared repository and the README contributor table. I kept my own entry up to date and made sure the student IDs were finalized early so that every member's work could be attributed correctly in the commit history.

When we walked through the Software Requirements Specification, I was drawn to the **Review Moderation** feature. The SRS describes how moderators must manually inspect reported reviews before any action is taken (FR-RM-01 and FR-RM-02), and that every moderation decision and its history must be recorded so moderators can recover from mistakes (FR-RM-05 and FR-RM-06). I argued in our discussions that the review moderation screen should give a moderator the same one-click workflow as the media page — a clear view of the queue, an explicit Verify/Flag decision per review, and an Undo action that reverts the last decision on that item. Recoverability mattered to me because moderators process many reviews in a shift and an accidental action must not be irreversible.

I also supported the team's testing strategy. We agreed that the frontend services (which sit between the pages and the API) are the natural unit boundary on the web app: they are small, deterministic modules that can be tested with mocked data and no network. That is the decision that let me add a Vitest suite for the restaurant, media, and review services alongside the Review Moderation page.

### 2.3 Feature Phase — Review Moderation Page and Service Tests (August 2026)

My main contribution is commit `Add moderation service unit tests and ReviewModerationPage` (`625208b`, 2026-08-11), which added 431 lines across the frontend.

**Review Moderation page (`ReviewModerationPage.tsx`, 204 lines).** This is the screen a moderator uses to act on customer reviews:

- A summary dashboard with three cards — Total Reviews, Language Verified, and Pending Review — so the workload is visible at a glance and updates live as moderations happen.
- Filter tabs (All / Verified / Unverified) to focus on the queue that still needs attention.
- A review card list where each review shows the restaurant name, a language badge, the review text, its star rating, and a Language Verified / Pending Review status badge.
- A **Verify Language** action to confirm a review's language, and a **Flag Language** action to mark it for review, each mapped to the `useSetLanguageVerified` mutation so the counters and badges stay in sync.
- An **Undo** button backed by `useUndoReview` that reverts the last moderation decision on a review, satisfying the SRS requirement that moderation history is maintained and actions are recoverable.
- Loading and error states: a spinner while reviews are being fetched, and a visible error banner when an undo fails (for example, when there is no recent action to revert) instead of failing silently.

**Frontend unit test setup.** I added `vitest.config.ts`, a `test` script to the web app's `package.json`, and `vitest` as a dev dependency, giving the frontend its first automated test runner.

**Service tests (22 tests across 3 files).** Each suite exercises the shared service layer against its mock data store:

- `restaurant.service.test.ts` (10 tests) — verifies `getAll`, `getById`, the `verify` review-threshold rules, and `checkData` / `setDataStatus` offensive-word scanning.
- `media.service.test.ts` (6 tests) — verifies `getAll`, `setVerified`, and the `undo` action history, including the error thrown when there is no action to revert.
- `review.service.test.ts` (6 tests) — verifies `getAll`, `setLanguageVerified`, and `undo` for language moderation decisions.

Running `pnpm test` in the web app now reports **22 tests passing** (3 files). The frontend also passes its lint and type-check commands with the new test files in place.
