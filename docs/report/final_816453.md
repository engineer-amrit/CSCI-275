## 1. Contribution to Team Discussions

As part of Team XOR I joined the group's discussions around how the moderation system should handle the content our users post on the restaurant review platform. During the early weeks in May I helped the team finalize the contributor list in the README so that all five members were properly credited, and I made sure my own student ID (816453) was listed correctly once the IDs were finalized.

When we discussed the moderation workflows, I was most interested in the media side of the platform. I raised the point in our meetings that restaurant images are one of the first things a customer sees, so moderators need a clear, visual way to approve or remove media — not just a text list. I supported the decision to keep media moderation as a manual task for moderators rather than automating it, because judging whether an image is appropriate requires human review. I also took part in the backend design conversations around how the moderation API should expose restaurant verification. We agreed the verification logic itself should live in a service, and the API should expose a thin controller that validates the incoming restaurant id and delegates to that service. That separation made it easy to unit-test the verification rules without spinning up a server, which was a design point I supported strongly. I also listened to feedback from my teammates about keeping the controller minimal and routing through versioned endpoints, and I applied that when I wrote the restaurant verification endpoint.

### 2.3 Phase Two — Feature Code (August 2026)

My main contribution is commit `Add media moderation page and restaurant verification endpoint` (`9b344c2`, 2026-08-11), which added 206 lines of code across the frontend and the backend.

**Frontend — Media Moderation page (`MediaModerationPage.tsx`).** This is the screen a moderator uses to review all media uploaded to the platform. It implements the media moderation workflow we designed together:

- A summary dashboard at the top showing total media, verified media, and unverified media, so a moderator can see the workload at a glance.
- Filter tabs to switch between all, verified, and unverified media, making it easy to focus on the queue that still needs attention.
- A card grid where each uploaded image is shown with its restaurant, a visible Verified/Unverified badge, and two actions.
- A **Mark Verified** / **Mark Unverified** action so a moderator can approve media that complies with platform guidelines or remove media that does not.
- An **Undo** button that reverts the last moderation decision on that item, which matters because moderators sometimes make mistakes and the SRS requires the ability to recover from incorrect actions.
- The page is wired to the shared media service and React Query hooks (`useMedia`, `useSetMediaVerified`, `useUndoMedia`), so its state stays in sync with the rest of the application and the moderation history is preserved.

The screen is not just a static list — every action maps to a mutation that updates the shared server-state cache and refreshes the counters and badges, so the dashboard numbers always reflect the latest moderation decisions. I also handled the loading and error states: while the media list is being fetched the page shows a spinner, and if an undo fails (for example, when there is no recent action to revert) the page surfaces a clear error message instead of failing silently. Those details are what make the tool usable by a moderator who might process dozens of images in a shift.

**Backend — Restaurant verification endpoint (`restaurant.controller.ts`).** On the API side I implemented the controller that exposes restaurant verification:

- A NestJS `@Controller` mapped to the versioned route defined in the shared contract package, so the frontend and backend always agree on the path.
- A `PATCH` handler that accepts a restaurant id from the URL, validated through the shared Zod validation pipe, and delegates to the injected `RestaurantService.verify()`.
- Dependency injection of the service, keeping the controller thin and testable, which was the design decision we agreed on in our discussions.

This commit is the implementation layer for two features from our SRS — media moderation (FR-MM-01 to FR-MM-04) and the API path that drives restaurant verification.
