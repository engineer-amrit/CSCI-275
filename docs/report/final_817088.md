## 1. Contribution to Team Discussions

Throughout the semester I took part in our team's planning and requirements discussions, focusing mostly on the user-facing moderation workflows and how the platform should handle content that gets reported. During the early scoping meetings in May I helped the team settle the contributor and meeting setup for the repository, and I made sure every member was listed in the README so ownership of the work was visible from the start.

When we moved into requirements, I joined the discussion on the moderation module and helped define how reports should flow through the system. I argued that reports needed a clear status lifecycle (pending, under review, resolved, rejected) so that both the user who submitted the report and the moderator handling it always knew where a case stood. I also stressed that the moderation system needed a queue for pending restaurant and review reports, because a moderator cannot review content the moment it is submitted — work needs to be batched and prioritized. My contribution to the SRS work on Reports Management came directly out of these conversations, and I drafted the functional requirements that describe how users report a restaurant or review, why they report it (reason), and how the moderator later dismisses or acts on the report.

Later in the design phase I focused on the frontend experience of the moderation tool. I proposed that the moderation console should feel like an admin panel with a persistent sidebar, so that moderators could move between restaurants, media, and reviews without losing their place, and that status counts (pending vs. verified) should be visible up front rather than buried in lists. I reviewed the proposed page structures with the team and gave feedback on which screens mattered most to a moderator's daily work — reviewing restaurants and logging in to the console. This turned into the two frontend pages I built at the end of the semester.

### 2.3 Phase Two — Frontend Development (August)

My largest contribution is the frontend work delivered in the final phase:

- `Add restaurant verification and login pages` (`6b9cda6`, 2026-08-11) — I built the two screens that anchor the moderation console: the **Login page** and the **Restaurant Verification page**.
  - The **Login page** (`LoginPage.tsx`) is the entry point to the moderation system. It has a branded split layout with a sign-in form, password visibility toggle, loading state, and error handling — making sure only authenticated moderators can reach the moderation tools, which is a hard requirement for a moderation system. It is wired to the shared auth service and React Query mutation hook, so the authentication flow stays consistent with the rest of the console.
  - The **Restaurant Verification page** (`RestaurantVerificationPage.tsx`) is the main working screen for moderators. It renders status cards at a glance — total restaurants, how many are verified, and how many are pending — and it makes clear that restaurant verification is automatic, based on customer reviews, so moderators cannot manually flip the status. Verified and pending restaurants are shown in separate lists with status badges, and the page includes a Restaurant Data Verification section where a moderator can expand any restaurant, review its title and description for offensive language, run an automated language check that flags matching words, and then mark the data as clean or flagged. The page uses the shared restaurant hooks (`useRestaurants`, `useCheckRestaurantData`, `useSetRestaurantDataStatus`) so its state stays in sync with the rest of the application.

This commit accounts for 601 of my 732 total insertions (82% of my code), and it directly implements two of the core moderation features defined in the SRS I helped author earlier.
