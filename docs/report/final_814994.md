## 1. Contribution to Team Discussions

Across the semester I took an active role in our team's technical discussions. When the team began to define what the platform would be, I pushed for a clear separation between systems rather than a single monolithic build. I presented the idea of splitting the platform into an authentication/rating service, a restaurant & vendor service, a discovery/search service, and a moderation system, and argued that the moderation system should be built as its own subsystem so that its review workflows could evolve without destabilising the rest of the platform. This is documented in the SRS I authored.

During requirements discussions I facilitated the group through the feature list, making sure every actor (guest, registered user, vendor, moderator, admin) had their needs captured. I volunteered to write the moderation SRS and ran the group through each functional requirement, which led to us tightening the restaurant verification criteria (minimum valid reviews, distinct users, average rating threshold) and agreeing that media and review moderation should remain manual tasks for moderators. In design meetings I argued for a shared contract package so the frontend and backend could share route/version definitions instead of duplicating them, and for mock clients behind interfaces so we could develop the API before the other teams' services were ready.

I also coordinated repository tooling decisions with the team — choosing pnpm workspaces with Turbo, ESLint and Prettier presets, and shared TypeScript configs — so every member experienced the same tooling. I handled the setup of the repository structure that the rest of the team builds on, and I documented our database/hosting plan. Where teammates worked in other areas (reviews, discovery, user auth), I made sure the contracts I authored referenced their services only through interfaces, keeping our integration points explicit in discussions rather than implicit.

### 2.4 Project Setup — Backend and Frontend (August 2026)

The final and most code-heavy contribution is the setup commit `Project setup for moderation module` (`f2235a7`, 2026-08-11), which moved the repository from documentation-only to a working monorepo:

- **Root tooling** — pnpm workspace definition (`pnpm-workspace.yaml`), the root `package.json` with build/lint/test/typecheck scripts, `turbo.json` pipelines, and a polished `.gitignore` covering build outputs, environment files, and TypeScript build info.
- **Shared packages (`packages/`)** — `config` packages for ESLint (`base`, `node`, `react`), Prettier, TypeScript and Vitest; a `common` package with contracts, primitives and Zod helpers; a `contract` package defining the moderation API versioned routes; `script` for deployment tooling; and `utils` packages (`uitls-config`, `utils-shared`) with shared helpers like contract validation and form utilities.
- **Backend setup (`apps/backend/moderation-api`)** — a NestJS scaffold with `AppModule`, `appInit` (versioning, cookie parsing, global exception filter), environment config validated through Zod, mock infra clients (`restaurant-client`, `user-auth-client`) behind interfaces, a health controller, exception filters, and the versioned `restaurant.v1` module structure. I intentionally left feature controllers for a separate commit so this commit remains purely the project scaffold.
- **Frontend setup (`apps/web/moderation-web`)** — a React 19 + Vite + Tailwind 4 scaffold wired to React Query, with the auth/report/support/restaurant services, typed domain models, and hooks. Page views were kept out of this commit to preserve it as setup only.
- **Microservice orchestration** — `services/setup.sh`, `config.json`, `docker-compose.yml`, and `Dockerfile.template` so the moderation API can clone and run the user-auth, restaurant, and search services during development.

This commit is the foundation the rest of the moderation feature work builds on, and it is the reason the whole team can develop in parallel with identical tooling and shared contracts.
